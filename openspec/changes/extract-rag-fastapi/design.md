# Design — extract-rag-fastapi

## Current architecture
`app.py` validates uploads and builds a `ConversationalRetrievalChain` directly; `ingestion.py`, `retrieval.py`, `llm.py`, `chat_state.py` and `config.py` supply supporting operations. Streamlit session state currently owns the vector store and chat history.

## Target flow
Streamlit (thin HTTP client) -> FastAPI (validation, schemas, routing) -> RAG application service -> PDF ingestion / FAISS+FastEmbed / Groq. Keep observability through sanitized structured logs.

## Decisions
1. **API boundaries:** `POST /api/v1/sessions/{session_id}/documents` accepts one PDF and returns a server-generated opaque document ID and indexing status; `POST /api/v1/sessions/{session_id}/questions` accepts a question and returns answer, retrieved page references and request ID; `DELETE /api/v1/sessions/{session_id}` clears state; `GET /health/live` and `GET /health/ready` expose lightweight service health. Final schemas should explicitly define typed errors and limits.
2. **Ownership:** The backend owns indexes and conversation history; the frontend stores only a session identifier and rendered messages. The backend must never trust a client-supplied document digest to authorize access.
3. **State lifecycle (local MVP):** use a bounded process-local session store with TTL, explicit reset, cleanup on failed uploads, and collision-resistant session identifiers generated by the backend (e.g. via `POST /api/v1/sessions`). Document that process restarts lose indexes and that multiple workers are unsupported pending shared storage. Do not assume a UUID alone authenticates users; local-only use is the scope. Do not expose the API publicly before implementing authentication, authorization and rate limiting.
4. **Isolation:** new uploads replace the session's index and clear chat history; requests cannot access other sessions' documents. Reject ask-before-upload; reject malformed, oversized, encrypted, excessive-page or text-empty PDFs using existing security limits.
5. **Execution:** PDF parsing and embedding are blocking operations; avoid blocking the async event loop (sync endpoints/threadpool or a bounded worker). Define timeouts, concurrency and request size protection at API and proxy boundaries.
6. **Errors:** use categorized status codes (400/413/422/404/503 as appropriate) and non-sensitive user messages with request IDs. Logs omit raw PDF text, keys and provider exception payloads.
7. **Tests:** unit tests for service, FastAPI integration tests with a real synthetic PDF and FAISS/FastEmbed when feasible, mocked Groq tests, isolation and failure-path tests; CI requires no secrets. Live Groq verification remains opt-in.
8. **Compatibility:** preserve Streamlit UX as much as possible. Keep FAISS and Groq adapters swappable, without adding speculative abstractions.

## Alternatives
- Embedded service-only refactor avoids HTTP overhead but does not demonstrate client/server boundaries; choose API for portfolio architecture.
- Qdrant would enable shared vector services but adds migration complexity before extracting the API.
- DuckDB is deferred; a process-local index is explicitly an MVP, not a production multiuser persistence guarantee.

## Rollout and rollback
Implement on a feature branch, run existing 12-test baseline plus new API tests, perform a local Streamlit-to-FastAPI smoke test, and review before merge. Preserve an easy rollback to the previous working main commit.
